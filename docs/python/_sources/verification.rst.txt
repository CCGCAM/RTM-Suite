Numerical verification against R
==================================

Every ported function has a ``pytest`` regression test comparing its
output against values generated by running the **original R package**
once, against current R source, and saving the results to CSV
(``python/scratch/scratch_export.R``). Reference CSVs are bundled under
each package's ``tests/refdata/``.

.. code-block:: bash

   cd python/toolsrtm && python -m pytest tests -q   # 32 tests
   cd python/scopeinpython && python -m pytest tests -q   # 18 tests

All 50 tests pass. Tolerance used in the tests is ``rtol=1e-6`` (loose, to
be safe across platforms/BLAS), but the *actual* observed differences are
at floating-point noise level except where noted:

No unresolved numerical discrepancies were found. Two things worth
knowing about, *not* discrepancies:

1. ``run_rtmo``'s ``rso``/``refl`` legitimately produce ``NaN``/``inf`` at
   far-thermal wavelengths where ``Esun_`` underflows to ~0 — this
   reproduces R's own behaviour at the same wavelengths.
2. ``soilwat``'s use of ``scipy.stats.poisson.pmf(round(mu), k)`` looks
   backwards at first glance vs. the natural ``pmf(k, mu)`` — this
   mirrors a quirk of the original R call ``stats::dpois(round(mu), k)``
   exactly, and is covered by the BSM regression test.

A genuine bug in R, found while porting ``getFluspect.Cx`` — since fixed
------------------------------------------------------------------------

``ToolsRTM::getFluspect.Cx``'s fluorescence-matrix code used to do
``Iwlf <- intersect(wlp, wlf)`` to locate the 640-850 nm fluorescence
emission band within the 400-2400 nm PROSPECT wavelength grid — but
``intersect()`` returns the matching *values* (640, 641, ...), which the
code then used as 1-indexed *positions* into the Kubelka-Munk
coefficients ``k``/``s``. Since the grid starts at 400 nm, this read
those coefficients at 1039-1249 nm instead of the intended 640-850 nm,
silently producing wrong ``Mb``/``Mf`` matrices on every call.
``ToolsRTM::getFluspect.B`` never had this bug (uses ``which()``, which
returns positions correctly), nor does SCOPEinR's own
``fluspect_Cx_forSCOPE.R`` (uses ``match()``). **Fixed in
``ToolsRTM/R/fluspect_Cx.R``** (now uses
``which(wlp >= min(wlf) & wlp <= max(wlf))``); :func:`toolsrtm.fluspect_cx`
updated to match, and the bundled reference data regenerated from the
fixed R source.

Several further real bugs were found the same way in
``SCOPEinR::get.RTMf`` and ``SCOPEinR::get.RTMz`` -- both now ported
(:doc:`scopeinpython/rtmf`, :doc:`scopeinpython/rtmz`):

- **``get.RTMf``**: a column-recycling issue (``nrow`` != ``ncol`` for
  the matrices involved), fixed with ``sweep()`` in 18 expressions total
  across two passes -- ``wfEs`` through ``sigbEplu_u/h`` (16), then
  ``Femmin``/``Femplu`` (2 more, found only once the Python port was
  written and its reference values disagreed with the first-pass-fixed R
  by a small but real amount, tracked down to this remaining instance of
  the same bug two lines further down); and an
  ``absfs_nl <- c(absfsfo)`` copy-paste mixup, fixed to ``c(absfs)``.
- **``get.RTMz``**: the exact same column-recycling family (including its
  own ``Femmin``/``Femplu``); its real output was only ever computed
  inside an unreachable ``if (get.plots == TRUE)`` block placed *after*
  the loop that produced its inputs, so normal calls silently returned
  the input unmodified (restructured to run unconditionally, inside the
  loop); a ``Po[1:nl+1]`` indexing bug (R parses this as ``(1:nl)+1``, a
  vector, not the intended scalar ``Po[nl+1]``); a hardcoded
  ``dim = c(30, 13, 36)`` (should be ``c(nl, 13, 36)``) in its ``etau``
  construction, silently wrong for any canopy with ``nl != 30``; and a
  MATLAB-to-R mistranslation, ``sum(LoF_, 2)`` (MATLAB's ``sum(A,2)``
  sums along dimension 2; R's ``sum()`` has no such argument -- it just
  adds the scalar 2 to the grand total and recycles that single number
  across every wavelength -- fixed to ``rowSums(LoF_)``).
- Two more possible issues in ``get.RTMz`` were **flagged but not
  independently confirmed or fixed** (unlike the above, which were all
  provable from R's own documented language semantics): an asymmetry
  where ``vfEplu_u`` uses ``fsctl_nl`` where the structurally-parallel
  ``vfEplu_h`` (and both of ``get.RTMf``'s versions) use ``foctl_nl``;
  and a second, separate ``data.Knu``-is-already-an-array code path that
  never applies the ``Kn2Cx()`` NPQ-to-zeaxanthin conversion at all
  (discovered while building this port's own R reference case, which
  originally passed an array there by mistake and got visibly wrong
  numbers as a direct result). See ``rtmz.py``'s module docstring for
  the full reasoning on both.
- **``RTMo.R``'s "lite" section-4 direct-beam term** (found while porting
  :func:`scopeinpython.rtmo.net_radiation_lite` for :doc:`scopeinpython/ebal`):
  ``Rndir <- fs_ * Asun[j]`` used ``j`` left over from an unrelated,
  already-completed ``for`` loop above it (always ``nl``, the *last*
  canopy layer), so direct-beam-absorbed net radiation on sunlit leaves
  came out **exactly constant across all canopy layers** -- confirmed via
  direct repro (``data.rad$Rnuc - data.rad$Rnhc`` had zero layer-to-layer
  variation), not physically sensible. Fixed to use the full per-layer
  ``Asun`` vector (a scalar ``fs_`` broadcasts correctly without
  indexing); a downstream ``Rndir[1] + Rndif`` (harmless before the fix
  since ``Rndir`` was a scalar, wrong after) fixed in the same edit.
- **``get.zo_and_d``'s degenerate-canopy branch** (found while porting
  :func:`scopeinpython.scope.get_zo_and_d` for :doc:`scopeinpython/scope`):
  when ``LAI`` or ``hc`` is near zero, ``zo_and_d$d <- d`` referenced
  ``d``, which is never assigned on that branch (only the sibling
  if-branch defines it) -- the same stray-variable bug pattern as
  ``RTMo.R``'s direct-beam term above. Fixed to the evidently-intended
  ``d <- 0``.
- **``ToolsRTM::SPART``'s ``get.plots`` handling** (found while building the
  AEO-Course practical, which calls ``SPART()`` directly many times with
  ``get.plots = FALSE``): ``if (missing(get.plots)) get.plots <- FALSE else
  get.plots <- TRUE`` ignored whatever value the caller actually passed and
  only checked whether the argument was *supplied at all* -- passing
  ``get.plots = FALSE`` explicitly got silently overridden to ``TRUE``
  (any explicit value forced ``TRUE``), while omitting the argument forced
  ``FALSE``, backwards from the function's own declared default
  (``get.plots = TRUE`` in the signature). Confirmed via direct repro: an
  explicit ``get.plots = FALSE`` call still printed ~6 internal ggplot
  figures per call (soil, irradiance, TOC/TOA comparison) and emitted a
  stray ``geom_line()`` "removed rows" warning; after the fix, neither
  happens, and the numeric output (``$output`` data frame) is unchanged
  (confirmed byte-identical). **Fixed** by removing the override entirely
  -- ``get.plots`` already holds the correct value via normal R argument
  binding, no ``missing()`` check was needed at all.
- **``ToolsRTM::Compute_BRF``'s ``short.waves`` handling** (found while
  building the AEO-Course PROSAIL app's RTM tab, which calls ``foursail``/
  ``foursail2``/``inform`` generically across all 5 leaf models): the same
  ``missing()``-vs-declared-default bug pattern as ``SPART``'s ``get.plots``
  above -- ``if (missing(short.waves)) short.waves = FALSE`` silently
  contradicted the function's own signature default (``short.waves=T``).
  Because ``rdot``/``rsot`` are 2101 long for PROSPECT-D/-PRO/Liberty but
  only 2001 long for Fluspect-B/-B-Cx (its native 400-2400 nm domain),
  omitting ``short.waves`` (every call site in the new RTM tab) skipped
  truncating the solar-irradiance vectors ``Es``/``Ed``, leaving them at
  2101 -- harmless for the three leaf models whose output also happens to
  be 2101 long, but for Fluspect's 2001-long output this length mismatch
  made R silently *recycle* ``Es``/``Ed`` against ``rdot``/``rsot``,
  wrapping back to the start of the spectrum for the last ~100 nm and
  corrupting the 2401-2500 nm tail with values from 400-500 nm instead of
  erroring or truncating correctly. Confirmed via direct repro (isolated
  ``rdot``/``rsot`` lengths per leaf model, then per-call
  ``withCallingHandlers`` warning capture pinpointing exactly the two
  Fluspect branches). Every *existing* call site (``SPART``,
  ``spart_simN``, ``inform`` via ``foursail.inf``) happened to already pass
  ``short.waves`` correctly matched to its own data, so none of them were
  affected -- confirmed by re-running ``inform()`` for Liberty and
  Fluspect-B-Cx against saved reference output before/after the fix
  (differences at floating-point noise, ~5e-16). **Fixed** by matching
  ``Es``/``Ed`` to ``rdot``'s actual length directly
  (``Es[seq_len(length(rdot))]``) instead of trusting a caller-supplied
  flag, making ``short.waves`` effectively redundant (kept only for
  backward API compatibility). ``inform()``'s own call chain in the Python
  port was never affected -- it already threads an explicit ``force_2001``
  flag through every call site before reaching :func:`toolsrtm.inform.compute_brf`,
  so lengths always match by construction there -- but calling
  ``compute_brf`` directly (not through ``inform()``) had the same latent
  gap; see the tenth bug below, found while verifying that exact usage.
- **``ToolsRTM::foursail2``'s missing Fluspect ``rsoil`` truncation**
  (found while verifying the fix above): unlike ``foursail()``, which
  truncates ``rsoil`` to ``[1:2001]`` in its Fluspect-B/-B-Cx branches,
  ``foursail2()`` never truncated ``rsoil`` at all -- so a caller's
  full-length (2101) soil spectrum was silently recycled against the
  2001-long green/brown leaf optics throughout the *entire* internal SAIL2
  radiative-transfer core (``rddsoil``/``rdosoil``/``rsdsoil``/``rsosoil``
  and everything downstream), not just at a single final step -- a more
  severe instance of the same recycling-instead-of-erroring failure mode.
  The function's own ``message('Please define same spectral domain for
  GreenVegetation and BrownVegetation and SpecPROSPECT')`` shows the R
  authors were aware a domain mismatch was possible but never enforced it.
  **Fixed** by truncating ``rsoil`` to ``[1:2001]`` whenever
  ``LeafModel %in% c('Fluspect-B', 'Fluspect-B-Cx')``, matching
  ``foursail()``'s established pattern exactly. No prior R or Python
  reference data covered this combination (previously untested); verified
  by cross-checking the freshly-fixed R output against
  :func:`toolsrtm.canopy.foursail2` (which already truncated correctly via
  its own ``force_2001`` handling) -- they agree to ~1e-15, and a new
  regression test/reference CSV
  (``test_foursail2_fluspect_b_matches_r_and_forces_2001``,
  ``ref_foursail2_fluspectb.csv``) now locks this in for both languages.
- **The Python port's own** :func:`toolsrtm.inform.compute_brf` **had the same gap as the eighth
  bug above** (found while verifying the AEO-Course PROSAIL app's tutorial code generator against
  all 15 canopy x leaf combinations, in both languages): calling it directly on a Fluspect-based
  ``foursail()`` result (2001-long ``rdot``/``rsot``) without also passing ``short_waves=True``
  raised a hard NumPy broadcasting error, since ``es``/``ed`` default to the full 2101-long
  irradiance columns regardless of ``rdot``'s actual length. ``inform()``'s own internal call
  chain was unaffected (see above), but any other direct caller of the public, exported
  ``compute_brf`` would hit this. **Fixed** the same way as the R-side eighth bug: ``es``/``ed``
  now truncated to ``len(rdot)`` directly instead of gated on ``short_waves``, which is kept only
  for backward API compatibility. All 33 ``python/toolsrtm`` tests still pass.
- **``ToolsRTM::getFluspect.B``/``getFluspect.Cx`` had their only ``return()`` statement trapped
  inside an ``if (fqe_ > 0)`` block** (found via a live crash while testing a new sensitivity
  sweep feature -- sweeping ``fqe`` from its own realistic range, which starts at 0, crashed
  immediately downstream): both functions compute ``refl``/``tran`` unconditionally, early in the
  function, but the block gating the fluorescence-specific (Mb/Mf) computation also contained the
  function's *only* return statement. ``fqe_ == 0`` (a valid input) made the whole function
  silently return R's ``NULL`` (``if (FALSE) {...}`` with no ``else``), which propagated through
  ``foursail()``'s ``rho <- LRT[[2]]`` into a **zero-length** ``rdot``/``rsot`` instead of an
  error -- confirmed via direct repro. **Fixed** by adding an ``else`` branch (all-zero Mb/Mf,
  physically correct for zero fluorescence quantum yield) and moving ``LRT``/``return(LRT)`` below
  the ``if``/``else`` so the function always returns a proper result. Zero regression against the
  existing ``fqe=0.01`` reference case (~5e-16). :func:`toolsrtm.fluspect.fluspect_b`/
  :func:`~toolsrtm.fluspect.fluspect_cx` had faithfully replicated this exact bug (returning
  ``None`` for ``fqe<=0``, with :func:`toolsrtm.canopy._leaf_optics` raising ``ValueError`` on that
  ``None`` as a defensive guard rather than a fix) -- updated to match the fixed R behavior:
  always return a proper result with all-zero Mb/Mf when ``fqe<=0``, and the now-unnecessary
  ``ValueError`` guard removed from ``_leaf_optics``. The two tests asserting the old
  "returns ``None``" behavior were rewritten to assert ``refl``/``tran`` match the ``fqe=0.01``
  reference exactly (never depended on ``fqe``) with all-zero Mb/Mf. All 33 tests pass.
- **``ToolsRTM::get.spectral.convolution.rfl()`` crashed on its own documented example** (found
  while checking the AEO-Course PROSAIL app's satellite-convolution tutorial against the R
  package's own docs): ``sensor.i`` is documented as a character string but the function passes it
  straight into ``get.coef.SMAC()``, which needs the actual bundled sensor object -- ``"subscript
  out of bounds"`` every time. **Fixed** by resolving a character ``sensor.i`` via
  ``get(sensor.i, envir = asNamespace("ToolsRTM"))`` before use. **A second bug in the same
  function**: its ``wave`` output column labeled bands using ``wl.smac`` in raw array order, correct
  only when ``id_smac_in_all`` is the identity permutation (true for Sentinel-2A/B and Landsat 8 by
  coincidence, not for Landsat 4/5/7, Sentinel-3A/B OLCI, or Terra/Aqua MODIS -- confirmed for all 9
  bundled sensors). **Fixed** using the same ``id_smac_in_all``/``band_id_smac`` re-derivation the
  AEO-Course app's own (already-tested) ``convolve_smac_sensor()`` helper used. Verified for all 9
  sensors: string/object dispatch agree exactly, documented example now runs cleanly.
- **New function, not a bug fix**: ``ToolsRTM::get.spectral.convolution.srf()``
  (:func:`toolsrtm.srf.spectral_convolution_srf` in Python) generalizes convolution for sensors with
  only a plain per-band SRF table and no SMAC coefficients -- PRISMA (never had SMAC coefficients)
  and Sentinel-2A/B via their separately-bundled plain tables (``srf.sentinel2a``/``srf.sentinel2b``,
  previously unused by any function). The AEO-Course app's private ``convolve_prisma()`` was removed
  in favor of this shared function (cross-checked byte-identical first). PRISMA convolution did not
  exist in the Python port at all before this; 4 new CSV data files exported
  (``python/scratch/scratch_export_srf.R``). Verified against R to full float precision;
  ``python/toolsrtm/tests/test_srf.py`` (3 new tests, including Sentinel-2A vs -2B being confirmed
  different real sensors) locks this in. All 36 ``python/toolsrtm`` tests pass.
